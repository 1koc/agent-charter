# collect/ —— 需求方 / 业务方对接

> **规则见 `index.md` §8.5（三层模型）与 §8.3（跨仓交接三要素）**。
> **一句话**：每个需求方一个目录；**根目录只放导航，业务内容一律进议题目录**。

---

## 一、目录范式（三层）

```
doc/collect/<需求方>/
├── README.md          ← L1 导航：索引 + 定位（本层只读）
├── summary.md         ← L1 导航：总览表（纯交接目录可用 README 代替）
├── require/           ← L1 导航：对端原文只读留档（不得改写）
└── <议题 1>/          ← L2 议题：一次需求/问题 = 一个目录
    ├── README.md      ← 议题索引（议题是什么 / 文件清单 / 溯源）
    ├── <方案与取证文档>
    └── 交付/          ← L3 交付层：对外自包含（禁 ../../ 引用）
        └── <产物>
```

| 层 | 硬约束 | 为什么 |
|---|---|---|
| **L1 导航** | 根目录**零业务内容文档** | 根一乱，找东西只能全文搜 |
| **L2 议题** | **单文档议题也各自成目录**；答不出归属的自成一议题 | 单文档散在根 = 下次追加没地方放，只能另开新文件 |
| **L3 交付** | **对外自包含**，物理含全部文档本体 + 产物，**禁 `../../`** | 接收方没有本仓访问权，相对引用等于死链 |

**命名**：需求类 `需求-NN-<主题>/`；问题/沟通/交付类 `YYYY-MM-DD-<主题>/`。目录名**不带**交付形态后缀（`-dll+交接文档` 之类）—— 交付形态由议题内 `交付/` 表达。

---

## 二、跨仓交接件（三要素，缺一不可）

落 `doc/collect/<对端>/<议题目录>/YYYY-MM-DD-<主题>-<对端>侧交接.md`。必备：

1. **本仓修改事实** —— 改了什么（文件 / 契约 `file:line` / 消息名 / 字段 / 协议）、当前状态（已落码 / 设计稿 / 零改动仅需对端适配）、可复现证据。
2. **必要性** —— 为何必须改、**不改的后果**（收不到 / 静默丢弃 / 契约对不上）、触发现象。
3. **对端需配合修改部分** —— **逐文件逐点清单**（`文件 → 改什么 → 说明`）+ **验收判据**（可判定）+ **回滚方式**。

> ⚠ 第 2 条最常被跳过。**写不出"不改会怎样"的交接件，通常意味着这笔改动其实不必让对方做。**
