### 1.6 验证按最小原则执行

**判据**：验证「某功能是否按预期工作」（字段/通道/接口是否出现、结构是否正确、是否报错或崩溃）⇒ 验证只是**功能判据手段**，不追求性能可比性。反例：为取性能基线、为定位热点而跑 ⇒ 属性能任务，不适用本条。

**执行口径（Rule 1「最小行动」在验证上的具体化）**：

- **只跑最小必要轮次**：功能判据取到即停。**不为墙钟波动、不为"复现性"追加轮次** —— 波动是环境噪声，功能验证里不是待解释差异，追加即越界。
- **不追求与历史基线可比**：不为对齐旧基线改参数、不补建运行环境、不比对耗时。这些属性能口径。
- **不改非必要配置**；确因功能需临时改的，**跑完立即还原默认值**，部署态不留测试态。
- **结论只写功能判据**：不与墙钟/吞吐纠缠。确需性能结论**另行按性能口径立项**（单独一轮、明示基线、控制变量）。
- **跑前先核对判据前置**：确认具备「产生判据数据」的前置（开关是否开、依赖是否就绪、几何/输入是否满足）。**前置不成立时跑多少轮都零结果**，正确动作是修前置、不是加轮次。
  - **「前置是否成立」必须查源码链路，不能只 grep 关键字字面**。

### 1.7 长任务必须有硬超时，到点即杀（2026-09-21 立规）

**硬约束**：凡自行拉起长任务（服务、仿真、批处理、大规模测试一律适用），**必须带硬超时、到点强制收进程**，不得依赖"跑完自己退"。

- **机制事实（通用）**：`sleep N |` 只决定 stdin 管道存活，**不是超时闸**；写端关闭后的 EOF 未必让目标进程退出。任何"到点自己会停"的写法**结构性无效**。
- **正确用法**：
  ```bash
  timeout -s KILL <N> <命令>
  # 到点被杀: exit=137
  ```
- **窗口量级先算再看**：按「预期时长 ÷ 加速倍数」估墙钟再定 N，不要凭感觉给。
- **收尾兜底必查**：超时之外仍须确认无残留进程 —— 残留会占用产物/端口，阻断后续构建与部署（表现"部署失败/半态"）。
- **窗口内收不到判据 ≠ 重跑**：先看判据取到没有，再决定是否重跑，别用"加轮次/加窗口"掩盖前置问题（同 §1.6）。

### 1.8 跨工程写入硬约束：非本仓一律「先申请、逐次同意」

**适用范围**：本仓之外的一切目录与文件，含但不限于：上游引擎/框架安装目录、兄弟仓、共享产物落点、他人的工作目录。

**硬约束**：

1. **写入前必须就「该次具体动作」取得用户明确同意**。任务性授权（"跑实测""修 bug""验证一下""继续"）**不构成写入授权**，不得推定；"同意改 A"只授权 A，不授权 B。
2. **覆盖一切写入形态**：新建/修改/删除/移动/覆盖/重命名/部署（含拷产物、安装、替换配置、改源码与脚本、写日志到别处）。
3. **申请须同时给出三项**：① 将被写入的**完整文件清单** ② 目的 ③ **回滚方式**（原文件备份路径或复原命令）。缺一不可。
4. **只读不受限**（Grep/Read/日志/进程查询等），但只读命令若产生副作用（如 `git status` 刷新 `.git/index` 时间戳）**须在汇报中如实声明**。
5. **违反即严重越界**：立即停手、回滚原状、如实报告影响面；不得隐瞒、不得"先做后补申请"。
6. 本仓内写入仍遵循 **Rule 1**（最小行动、不多做、逐意图确认）。
7. **本条约束 AI 的决策，不约束既有工程链的功能**：
   - 既有部署链（构建脚本 `install` 分支、CI 既有的拷贝/安装动作）属**常规工程动作**，AI 执行**不算越界写入**，落点按**工程事实**如实报告即可，**无需**逐次申请。
   - 需申请的只有 **AI 主动改部署目标/改构建脚本/改配置/换投放路径/新增投放点** 这类**决策**。
   - **本地测试部署免备份**：测试环境的产物部署**无需备份、无需逐次申请**。备份权威来源 = 构建产物（同 §9），回滚 = 重建后重部署。

**自检判据**：答不出"这次写入的授权来自用户哪一句明确表态"即越界。**反向自检**：把既有构建链的常规执行也当成"需申请的写入"即过度约束（第 7 条）。

### 6. 方案完成与归档规则

- **完成标准**：方案实施到**编译通过**即视为完成（有单测的方案以**单测通过**为准）；不等待集成/场景验证。
- **归档**：完成后方案移入 `doc/archive/`，命名 `时间戳+原名`（`yyyy-MM-dd-HH-mm`），状态改「已落地」；同步从 `doc/todo/README.md` 移除该行。
- **自动 ADR**：每次方案落地后新建一条 ADR（编号递增），登记 `doc/adr/README.md` 状态总表与推翻/扩展关系图，并更新 `doc/ref/project.md`「当前架构权威 ADR」表述。
- **推翻标注**：新决策推翻/部分推翻旧 ADR 的，须在状态与关系图显式标注（`Superseded` / `Partially Superseded by #N`）；被取代文档同步标注并指向新方案。

### 7. 遗留问题登记规则

- **落账范围**：方案落地后未解决的遗留（未接入路径、后续阶段、待人工复核等）、测试发现的问题、其他未解决问题，一律登记 `doc/todo/遗留问题.md`。
- **登记时机**：发现即登记，不攒不拖；方案落地时同步查遗留尾巴，有则补登。
- **登记方式**：在对应「项目更迭」分组下追一行（无分组则新建小节），登记问题、初始状态与来由。
- **解决清理**：问题解决后**从本文件删该条目**，解决方式写入对应 ADR/设计文档/代码注释；本文件只含未解决问题，防膨胀。

### 8. 文档引用与维护规范（防「代码一动文档大面积更新」）

- **文档三分层**（按「是否随代码演进」划分）：
  - **层 A｜冻结区（不回填、不维护）**：`doc/adr/` 下的 `NNNN-*.md` 决策正文快照（**不含** `doc/adr/README.md`）、`doc/archive/`（已落地方案）、`doc/chaos/`（过程材料）、`doc/origin/`（原始资料）。记录的是*当时*状态，失效链接**允许存在、禁止回填**（回填即篡改历史）。
  - **层 B｜活文档（唯一维护区）**：`doc/collect/`、三个索引（`doc/README.md`/`doc/adr/README.md`/`doc/todo/README.md`）、`doc/todo/遗留问题.md`、`doc/ref/`、`doc/reuse/`、`doc/note/`、`doc/research/`。只有本层要求 0 坏链、随代码同步。
  - **层 C｜单一事实源（SSOT）**：**分工两件套** —— ① **状态与取代/扩展关系**唯一维护在 `doc/adr/README.md`（状态总表 + 关系图，**层 B 活文档**）；② **决策正文**为 `doc/adr/NNNN-*.md`（**层 A 冻结快照**）。一句话：正文答「当时决定了什么」，README 答「现在还有效吗、被谁取代/扩展」—— 因明细冻结、后续状态写不进去，**状态只能落在 README**。`doc/README.md` 只放指针，禁止两处维护同一内容。新 ADR 编号取明细与状态总表编号的**并集最大值 + 1**。
- **目录归置硬约束**：**`doc/` 根只允许 `README.md`**（索引本身），其余一切文档必须落子目录 ——
  | 目录 | 放什么 |
  |---|---|
  | `doc/todo/` | 演进**方案**（一方案一文件，落地后进 `doc/archive/`） |
  | `doc/research/` | 方案**前置**的现状与边界取证（调研/可行性/能力边界；**非实施方案**，禁止搁 `doc/todo/`） |
  | `doc/archive/` | 已落地方案归档 |
  | `doc/adr/` | 架构决策记录（不因状态流转迁移目录） |
  | `doc/bug/` | 缺陷定位与修复记录 |
  | `doc/note/` | **要点/结论型短记录**（一句话要点 + 证据 + 处置），一要点一 md |
  | `doc/reuse/` | 规范与可复用范式（见 §8.7） |
  | `doc/ref/` | 从 `index.md` 按需拆出的重型参考 |
  | `doc/collect/` | 需求方/业务方对接（见 §8.5） |
  | `doc/chaos/` | 过程性/过时材料（内容不作准，仅溯源） |
  | `doc/origin/` | 原始资料，只读 |
  - **`_` 前缀 = 索引 / 模板 / 辅助件**（`_目录.md` / `_template.md`），**内容文档禁用 `_` 前缀**。
  - **新增文档时先确认归口目录**，禁止直接写在 `doc/` 根；归口不明确时先补目录/索引。
- **引用写法**（优先级：**符号 > 路径 > 行号**）：
  - 指源文件 → **仓库相对路径**；禁止 `file:///` 绝对路径超链接（换盘符/迁移即断）。
  - 指函数/逻辑 → **符号定位**（`src/x.cpp :: Func()`）；**不写行号**，行号仅在 ADR 作「当时快照」并标注「以当时版本为准」。
  - 指契约字段 → **不复制清单**，写「见 `inc/Xxx.h` 的 `XxxStruct`」。
  - 跨文档 → **不复制内容**，链接 + 一句摘要。
- **效果**：把「改代码 → 改文档」从全仓大面积收敛为「仅架构决策/接口契约变更才动文档」；**行号漂移与文件移动不再触发文档更新**。

### 8.1 文档阅读顺序与冲突裁决

- **倒序阅读**：查阅任何**文档记录**（ADR、archive、chaos、周报/日志等按时间累积的记录）一律**从最新往旧读** —— 先看编号最大/时间最新的一份，确认是否已取代、扩展或推翻旧内容，再按需回溯。**禁止从 #1 起顺序通读**：既慢，又易被已废止的旧决策误导。
- **先索引后明细，读到为准**：ADR 先读 `doc/adr/README.md` 状态总表（只取 `Accepted` 且未被取代者），再按倒序读明细，**读到结论明确即止**。
- **冲突裁决优先级：实际代码 > 活文档 > 历史记录**。文档与代码不一致、多份记录互相矛盾、或表述含混时，**一律以当前源码（及实测运行输出）为准** —— 代码是唯一事实源，文档只是对*当时*状态的描述。发现冲突须**指明具体位置（文件/符号 + 文档名）并说明差异**（Rule 2），不得默认文档正确，也不得静默按代码行事而不告知。
- **改判即回写**：若代码现行做法已不同于文档记载，按 §6/§7 处理 —— 架构性差异走新 ADR 并显式标注取代关系，未决分歧登记 `doc/todo/遗留问题.md`；**禁止回填历史文档**（§8 层 A）。

### 8.2 外部接口主张须三方对照核查（有外部依赖时启用）

> **立规缘由**：方案里写"引擎/上游库有 X 方法"却按内层命名写、与上层暴露面层级错位 ⇒ 功能等价但形态不同，反复对不上、返工。

- **触发**：一切**引用外部依赖（引擎/框架/上游库/第三方 SDK）接口**的文档主张，凡出现**方法名 / 签名 / 参数 / 单位 / 类归属**的判断，均须按本条核查。
- **核查基准（三个来源，都要）**：① **上层/脚本文档**（表达口径以此为准：公开名 + 签名 + 单位）；② **内层源码**（行为口径以此为准：真实实现、`file:line`）；③ **包装层**（有则必查：上层名 ↔ 内层名的映射、类型转换与单位换算 —— **这是"对不上"的高发区**）。
- **硬要求**：三方对照各给 `file:line` + 原文；判定必须明确（`一致`/`不一致`/`无对应`），`不一致` 须写清差在哪（命名映射？层级归属？参数个数？单位？`deprecated`？）；"无对应"须区分「上层无但内层有」「上层有但归属不同」「两层皆无」。
- **自检判据**：① 有归属断言却无出处？② 引内层签名却未核上层是否有同名/更简暴露面？③ "没有 X"的**否定性结论**未在上层文档全文检索确认？④ "需自建/自行转换"的成本结论未核包装层是否已做？⑤ 单位是否逐条标了来源？

### 8.3 跨仓/跨端改动须文档化交接

> **立规缘由**：跨仓协作中，单边改动常在"对端未配合"时**静默不生效**（新 topic 无订阅、新字段无消费、新协议对端不认）。此类依赖若只散落在会话消息里，必丢失。

- **触发**：本仓任一项改动，若其**生效/可验证/可交付**依赖**非本仓**（对端后端、前端、引擎、其他服务）配合修改。**纯本仓自洽改动不适用**。
- **归口**：`doc/collect/<对端>/`。
- **命名**：`YYYY-MM-DD-<主题>-<对端>侧交接.md`。
- **必备三要素（缺一不可）**：① **本仓修改事实**（改了什么：文件/契约 `file:line`/topic/字段/协议；当前状态；可复现证据）② **必要性**（为何必须改、**不改的后果**、触发现象）③ **对端需配合修改部分**（**逐文件逐点清单** + **验收判据**（可判定）+ **回滚方式**）。
- **与 §1.8 的关系**：**§1.8 管"写非本仓须逐次申请"，本条管"跨仓依赖须留痕"**。二者并行：一旦确认要动对端，**先出交接文档 → 再按 §1.8 申请**。
- **自检判据**：答不出「交接文档落在哪个文件」即违规；反向自检：纯本仓改动也强写交接件属过度。

### 8.5 需求方/业务方目录三层化

- **规则条文（三层）**：
  1. **L1 导航层（只读）** = `README.md`（索引 + 定位）+ `summary.md`（总览表）+ `require/`（**对端原文只读留档**）。**硬约束：根目录零业务内容文档**。
  2. **L2 议题目录** = **一次需求 / 问题 = 一个目录**；内含 `README.md`（议题索引）+ 该议题全部文档。**硬约束：单文档议题也各自成目录**（不散落根）；**答不出归属的文档，自成一议题**。
  3. **L3 交付层** = 议题内 `交付/`；**对外自包含**（物理含全部文档本体 + 产物），**禁 `../../` 相对引用**（接收方无本仓访问）。
- **命名**：需求类 `需求-NN-<主题>/`；问题/沟通/交付类 `YYYY-MM-DD-<主题>/`。目录名**不带** `-dll+交接文档` 之类交付形态后缀。
- **与 §8.3 关系**：§8.3 管"交接件的必备三要素"，本条管"交接件放哪、怎么组织"。
- **自检判据**：根目录出现业务内容文档、或议题目录缺自身 `README.md`、或交付包含 `../../` 引用 ⇒ 违规。

### 8.6 部分全自动执行流程：分段 + 检查点

> **立规缘由**：一次「人工拍板、AI 连跑到黑」的单轮实测吃掉会话 **47.7%** 额度，其中 **44.7% 是上下文重发税**（与工作量无关，只与「上下文大小 × 步数」有关）。大任务改「分段 + 检查点」，把成本从**事后分析**变为**事前门控**。

- **判据**：任务**较大且可切段** ⇒ 分段；小任务连跑（切碎更贵）。
- **段边界**：只画在**有客观验收命令**处（编译过 / 测试过 / e2e 数值），不画在「感觉该停」处。
- **检查点**：默认**同会话**继续（零额外人工，但省不掉重发税）；仅当上下文逼近天花板或步数远超预估时，**助手提示、由人拍板切新会话**。
- **落点**：R0–R4 分段表 / 检查点简报模板 / 阈值与协议细则见 `doc/ref/segmented-exec.md`。
- **自检判据**：大任务答不出「段边界落在哪条验收命令」即违规分段；小任务强分段属过度。

### 8.7 `doc/reuse/` 可演进范式区：双源机制 + 成熟度标记

- **定性**：`doc/reuse/` = **层 B 活文档，可演进**（非冻结区）。它与层 A 的差别不是「成熟度」，而是**「可否改」**：层 A 记录*当时*状态故不可改；层 B 记录*当前*有效口径故必须随现状改。

- **双源机制（两种来源，缺一不可）**：

  | 来源 | 形态 | 特征 | 落点要求 |
  |---|---|---|---|
  | **① 经验归档型** | 从**已发生**的实践中提炼 | 须有**实测证据**（行号/命令输出/编译结果）；结论已基本稳定 | 一条机制 = 一句话结论 + 为什么 + 复现动作 |
  | **② 范式构建型** | **先立结构**，边用边完善 | 结构已立但**实践未走完**；须显式标注**待验证区** | 头部标「**构建中**」，写明**升级条件**与**首个实践对象** |

- **②不是①的前置或替代**：一次实践走完前，①**无法从零**总结（结构尚未被现实检验）⇒ 先以②立结构，用它走一遍，走完才沉淀为①。**② → ① 的转段以「升级条件满足」为准**，不由主观判断。

- **成熟度标记（每件头部必写）**：
  ```
  成熟度：构建中（结构已立，实践对象=待填）｜ 已验证（实证 ≥1 次完整实践并已回填结论）
  ```
  **状态可逆**：实践暴露结构缺陷 ⇒ 退回「构建中」并注明「因 X 实践被证伪/不足」；**不得删除历史结论**，改为标注失效（行内 `~~删除线~~` + 指向新结论）。

- **档内读法补充**：§8.1 定总档位「代码 > 活文档 > 历史记录」并对历史记录要求倒序读；本条补**同一档内以新的为准**：两份记录对同一事项结论不同时，采**编号大/时间新**者；被采旧者**不删除、不改写**，只由新记录声明取代关系。⚠ **只在历史记录内部生效**，不适用跨档位。

- **准入门槛**：新落 `doc/reuse/` 须**已在本仓或他仓用过至少一次**；纯设想先落 `doc/todo/` / `doc/research/`，用起来再沉淀。

- **自检判据**：出现「某经验不知该落 `doc/reuse/` 还是 `doc/todo/`」⇒ 违规（应能依本条判出）；`doc/reuse/` 新件缺成熟度标记 ⇒ 违规。

### 8.8 呈报闸 / 动手闸 / 原文闸：三条强制自检

> **立规缘由（可查）**：曾在同一会话内连续违反 `AGENTS.md` §5 —— ① 把「逐个裁决，按约束来」读成「由 AI 按约束代裁并落码」，越步到写码/编译/跑测/回填台账；② 六件套齐全但**漏「显式推荐 + 理由」与「每项代价」**。两次均**非规则歧义**，而是执行时缺闸门、且以压缩摘要代替规则原文。

**闸 1 · 呈报闸（发决策点前逐条过，缺一不得发出）**

本节是**合并检查表**：`AGENTS.md` §5.1 三段式 + §5.2 六件套 + §5.3 十条判据**一次过完**，禁只照其中一张。

| # | 检查项 |
|---|---|
| 1 | 给了批次总表（议题/依赖/批序），且总表内**无选项、无推荐、无利弊** |
| 2 | 只展开当前批；批内只报一个议题 |
| 3 | 自包含事实就地给全（不靠用户回忆） |
| 4 | 被改动/依赖的代码**贴原文**（禁只给行号） |
| 5 | 逐行/逐块释义讲到**机制因果** |
| 6 | 每个选项写明**目标形态** |
| 7 | **每个选项逐项写代价/优缺点**（不是笼统一段「后果」） |
| 8 | 末尾有「**推荐 X —— 一句话理由**」（禁以「看您」回避） |
| 9 | 影响面文件清单 + 回滚方式 |
| 10 | 末尾**复述待表态项与期望代号** |

**闸 2 · 动手闸（任何写文件/编译/跑测/改文档/回填台账前，先在心里填这一句）**

- 本步动作 = ______；**用户已明确表态的范围** = ______（引用代号或原话）。
- **范围不含本步 ⇒ 停**。例外仅两类：① 用户显式整包授权（「全做」「直接改」）；② §1.5 预授权读取、§1.8 豁免项。
- **典型越步形态**：判定「选 a」后直接写头 → 改缓存 → 写单测 → 编译 → 跑测 → 回填台账。**每一步单看都自洽**，所以没有任何一步会触发回头核对授权 —— 闸 2 的唯一作用就是在**第一步之前**问这一句。
- 附带：**提案中的"推荐"不是授权**；「AI 认为该做」也不构成授权。

**闸 3 · 原文闸（长会话 / 上下文压缩后必过）**

- 压缩摘要里的规则转述**不得作为依据**：摘要会丢强制语气与编号（曾出现摘要写作「先列选项 + 优缺点 + 推荐」，于是「必给」的强制性消失）。
- 发决策点或动代码前，若距上次读规则已隔一次压缩或长间隔，**先回读 `AGENTS.md` §5 + 本文件 §8.8**，之后再动手。

**自检判据（任一即违规）**：决策点缺「推荐 + 理由」或选项代价未逐项 ⇒ 违闸 1；未获代号表态即写文件/编译/跑测/回填文档 ⇒ 违闸 2；把压缩摘要当规则出处 ⇒ 违闸 3。

### 9. 部署态：无备份往返

- **部署目录不是备份仓**：产物落点只存放"当前要生效的产物"。禁止在其中生成任何备份副本 —— `*.bak`、`*.prev*`、`*.off_*`、`*.old` 一律不留。
- **切换配置态 = 直接覆盖 / 直接删除**：切构建档一律覆盖正式文件名，**不先备份**；停用某产物**直接删除**，**不得改名**成 `*.off_*` 当停用手段 —— 改名副本会被当成"部署态的一部分"，反而掩盖真实状态。
- **备份的权威来源 = 构建产物（唯一可信）**：从部署目录删掉产物**不丢东西**，随时可重建取回；**须与源码同步重建，未重建即为陈旧**。
- **判态用字节统计/符号计数**，不用 md5/时间戳对表（后者易被拷来拷去骗过）。
