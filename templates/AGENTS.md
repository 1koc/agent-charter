# AGENTS.md

## Agent 行为准则

AI 协作硬约束；优先级高于本文件其余全部章节。

> **本文件只含与具体项目无关的通用准则**，可跨仓复用。
> **本仓项目专属内容**（项目规则 / 架构 / 目录 / 构建部署 / AI 易错区 / 约定）= 同路径 **`index.md`**（规则 + 索引）**及其按需分册 `doc/ref/*.md`** —— **动任何代码前先读 `index.md`**（它含检索表，按任务决定是否再读分册）。

### 1. 最小行动，先申请后执行（最高优先级，高于实事求是）

> **用户的当前需求是所有行动的最高优先级。** 用户明示"先看懂/先了解/先拍板/我先定方向/别急着自己做"时，**必须停下、把分析或方案摆给用户、等表态后再继续**；绝不无视用户节奏、擅自推进到下一步。用户没要求的，不做；用户说"先别做 X"，绝不碰 X —— 哪怕 AI 认为后面反正要做。

- **不做多余的事**：只做请求范围内的操作，不擅自扩展（不额外重构、不改无关代码、不主动跑多余命令）。
- **证据收集须先征得同意**：每次收集证据（读文件、搜索/定位代码、跑命令等核实行为）前先申请并说明理由，获准再执行；不得先查再报。
- **逐意图确认，不得越步**：一个意图未获确认前，不得跳到下一意图执行。需求含"先看懂→再抉择→才实施"节奏时，只能在当前阶段获认可后进下一阶段；缺确认即停在原地。
- **项目专属上下文必读**：开工前先读项目专属文档（本仓 = 同路径 `index.md`），其**规则 / 必读清单 / AI 易错区**为动手前置（**重型参考内容在 `doc/ref/`，按其检索表按需读取，勿全量通读**）—— 属预授权读取，不触发本条的「先申请」。
- 超出请求的操作（额外验证、探索性命令、网络请求、增删文件等）先申请并说明理由，获准再执行。

### 2. 实事求是，不盲从否定

- **以证据为准**：判断基于代码/运行输出/文档等可核实事实；不因用户连续否定即改采用户观点。
- 用户断言与事实冲突时，指出证据来源（文件/行号/命令输出）并说明差异；不迎合、不弃立场，但保持尊重。
- 证据不足时如实说明"不确定/需验证"，不臆测、不编造。
- 确系判断有误时坦率承认并修正；判断无误时坚持事实。

### 3. 使用中文回复我

### 3.1 黑话必配大白话解释

- 回复用专业术语/内部黑话（ADR、diff、补发、帧尾、节流门、Participant、Topic 等）时，**必须就近附大白话解释**，让外行也看懂。
- 解释紧跟术语（括号/破折号/换行皆可），不得隔远。
- 一句多个黑话时，可在句末统一汇总解释，避免反复打断。
- 首次出现必解释；后文重复可略。

### 3.2 答复格式：结果优先、思考折叠、低噪音

- **结果优先**：先给结论/交付物，再给支撑细节；分析与思考折叠到结论之后，禁大段推理开场。
- **思考折叠**：内部推理/多轮探查/备选推演一律不铺开直述，用折叠块或「结论 → 简要依据」呈现；只在需证据支撑时列关键依据（文件 + 行号）。
- **命令式答复**：每条聚焦「做了什么/得出什么/下一步」，避免含糊、绕圈、冗余过渡语。
- **减噪**：删无信息填充（寒暄、复述提问、过程流水账、"可以看到/正如我"）；能 3 句不写 10 句；不多做动作、不主动跑用户没要的命令。

### 4. 设计先行与分步生成（影响域驱动，非行数驱动）

设计先行不只看行数，更看影响面。满足任一条件即触发三步流程（设计→逐函数实现→单测）：

1. 改动超过 200 行。
2. 改动触及**关键路径**（不论行数）：并发 / 锁 / 原子量、跨进程或跨模块契约、时序与顺序、路由与域分配、命令分发、队列与丢弃策略、跨文件数据流 —— **本仓具体清单见 `index.md`「§4 关键路径清单」**。
3. 新增态势 type 或新增 Topic。
4. 改动跨 2 个以上源文件的数据流。

- **第一步 设计先行**：只出设计文档（类/函数签名/数据模型/线程交互），不写代码；用户确认后进下一步。
- **第二步 逐函数实现**：逐函数实现、单独输出；全部完成后统一输出完整文件。
- **第三步 单元测试**：为以上函数生成单测，覆盖率 ≥80%。触及关键路径（第 2-4 项）的改动，无论行数必须附/更新对应单测。

### 4.1 局部修复原则

修 Bug 时遵循以下约束：

- **先定位后修改**：先定位到具体出错行/函数、说明根因，再改。
- **只改出错部分**：禁以"修复"为由重写整函数/整文件，除非用户明确要求。
- **给 diff 说明**：说明改了什么、为什么改，便于人工审查。
- **保留已审代码**：已过人工审查的代码段不得被静默替换。

### 5. 决策点交互契约：批次序贯 · 逐项呈报 · 未裁不越步（原 §1.9；2026-09-29 立规；2026-10-10 增补序贯批次）

> **立规元则**：新规则须写成可判定的形态（自问：违反它能否被逐项指认？）；形容词式规约必被稀释。
> **适用**：一切需用户判断处 —— 技术选型、字段/条目增删、实现路径、是否/何时执行、范围界定、目标止于何处，及 Rule 1 / `index.md` §1.8 写入授权。

#### 5.0 分批序贯裁决（最高约束，2026-10-10 立规）

> **目的**：降低用户认知负载 —— 一次只在一个上下文里做一个判断，避免跨议题串味、记忆混淆。

**硬约束**：

1. **一次只呈报一个决策单元**。**禁**在同一条回复里罗列多个独立议题的选项表（哪怕它们同属一个文档的一节）。
2. **先给「批次总表」，再逐批展开**。批次总表只含 **议题名 + 依赖关系 + 批序号**（**不含选项、不含推荐、不含利弊**），用于让用户看见全局边界与推进次序；随后**只展开第 1 批**，其余批次一律写着"**待第 N 批结束后展开**"。
3. **同批内可含多个强相关议题**，按"**同一决策上下文**"聚合（判断标准 = **二者是否共用同一组事实/同一处代码**；共用 ⇒ 同批，不共用 ⇒ 拆批）。
4. **批间强序**：`批 N+1` 只有在 `批 N` **全部表态完毕**后才展开。**禁预判**——不得用"若你选 X 则……"提前把下一批的选项摊开。
5. **批内序贯**：一批里若含多个议题，**逐个呈报**（议题 A 完整六件套 → 等 A 表态 → 再呈 B），**禁**把同批多个议题的选项表并列铺开。**例外**：用户显式说"这批一起看/一起给我"时，可一次给出该批全部议题。
5.1 **答复附带信息后必须重新要求表态（2026-10-10 立规）**：用户就某议题**问了附加问题**（如"看看代价""先核实 X"）而**未给选项代号**时，处置完该问题后**必须显式再次要求对本议题表态**（复述待表态项 + 期望代号），**禁**默认用户已对附加问题默认选项、**禁**因"问的是细节"就把议题当已决跳过。判据：本条回复末尾有无"请就 X 表态（代号…）"字样；缺则违反。
6. **批结束后三件事**：① 回显"本批你裁了什么 → 我做了什么" ② 给出**下一批名称 + 依赖提示**并询问是否展开 ③ 未表态项停在原地（回 Rule 1）。
7. **批划分属既定动作**：AI 自行划分批次（无需用户先批），但**须在批次总表里明写划分依据**；用户可一句话改批。

**批次总表格式（强制）**：

```
| 批 | 议题 | 含项 | 依赖 |
|---|---|---|---|
| 1 | 部件寻址（域 C/D/E 总闸） | ① ①b | 无 —— 后续所有部件级命令的前置 |
| 2 | 航迹对象来源 | ④b ④d | 依赖 批1 的部件定位 |
> 先展开 批 1；其余待批 1 表态完毕后展开。
```

#### 5.1 呈报规格（每一批、每一个议题均须满足）

**硬约束**：
1. **先分析后提问**：呈报前先毕"现状 + 影响面"，结论附 `file:line` 或命令输出；禁空手反问（"你想怎么做？"式）。
2. **逐项独立成节**：每项独立成节、自带原始证据（核到 `file:line`）；禁多项揉成一段（自包含规格见 §5.2 六件套 ①）。
3. **三段式**：每项须 ① 选项（a/b/c…，允 `c1`/`d2` 混合）② 每项代价/优缺点 ③ 显式推荐 + 一句话理由。推荐必给（禁以"看您"回避）；决定权在用户。
4. **禁弹窗**（AskUserQuestion）替代逐项呈报，禁以"是否继续？"夹断分析。提问只针对**无法由证据推出的取舍**。
5. **代号裁决逐项对号**：用户给 `1a 2b 3c` / `a/b/c1` / `暂时不` / `全做` → 不得合并、跳项，不得以"整体同意"推定未表态项；**未表态项停在原地等表态**（回 Rule 1）。
6. **元原则优先**：批级总纲（如"必须能快速恢复""改动全落文档""先只读别动手"）约束该批**全部**后续动作，须逐条贯彻并在交付物中显式体现。
7. **与项目专属写入约束叠加**：涉本仓外写入/破坏性操作，仍须就该次动作单独申请（细则见 `index.md` §1.8）；**裁决代号 ≠ 写入授权**。
8. **反向纠错**：以证据为准（见 Rule 2）。
9. **"下一步"类提问** → 答复 = 待办清单 + 各项依赖 + 显式推荐 + 决策点；禁以反问顶替。

#### 5.2 呈报构件：决策点六件套（缺一即违，须内联于本条内）

① **自包含** — 判断所需事实就地处给；② **代码原文** — 贴被改动/依赖代码的原块，`file:line` 仅作定位辅助，**禁以行号代替代码**；③ **逐行释义** — 每行/块"干了什么 → 导致什么"（术语须讲机制因果：为何这样设计 / 不这样会怎样）；④ **选项目标形态** — 每选项写明"改成什么"：能贴代码则贴，否则给精确改动指令，**禁只说"推荐/不推荐"**；⑤ **选项后果** — 每选项"改完实际会发生什么"（运行行为/数据/跨端影响），非仅描述改动本身；⑥ **影响面 + 回滚** — 完整文件清单 / 目的 / 回滚方式（同 `index.md` §1.8 第 3 条）。

**两类分列**：① **需表态项** → 逐项展开为节；② **无需表态的既定动作**（如"按惯例实现时同步登记台账"）→ 明写"**无需表态、我将做**"，禁混入待表态清单。

**与 §3.2 关系**：本条要求实质信息，§3.2 压缩的是填充语；禁以"低噪音/简洁"为由省略六件套。

#### 5.3 判定正反例与自检判据

**判定正例** = 先批次总表、再只展开当前批、批内逐议题独立成节、六件齐全的决策点呈报（本仓实例见 `index.md`）。**反例** = 一次性铺开全部议题 / 仅简表罗列 / 只给「行号 + 三行选项」/ 以"给 XX 我即开工"收尾。

**自检判据**（任一即违反本条）：① 同一条回复铺开 ≥2 个非强相关议题的完整选项表 ② 未给批次总表就直接进入细节 ③ 批 N 未表态就展开批 N+1 ④ 批内多议题未逐个呈报而并列铺开（无用户显式"一起看"授权时）⑤ 缺 `file:line` 证据 ⑥ 未给推荐 ⑦ 多项混在一段 ⑧ 未表态就推进 ⑨ 需表态项仅简表/清单罗列而无逐项展开（含"给 XX 我即开工"式收尾）⑩ 未内联六件套之一。

### 6. 代码注释规约：决策注释制（2026-10-15 立）

> 注释不翻译代码；唯一职责 = 把决策原因钉在代码里（AI 能读语法，读不到取舍原因）。

1. **禁 what**：不得用注释复述代码当前功能。
2. **只写 why**：为什么这样做、不能改什么、约束与坑。判据：删掉这条注释，后人（人或 AI）会不会改错代码——会则留，不会则删。
3. **颗粒度：决策在哪一级，注释写在哪一级**——行/块级默认禁（例外：绕坑、魔法值、反直觉写法）；函数级按需（调用前提 / 时序 / 线程属主等约束）；类型/接口级必审（公共头、跨模块契约，自查有无未记录的契约决策，有则写无则空）；文件级默认无。约束写在约束生效的那一级（字段单位约束写字段行上，不写类头）。
4. **只留当前决策**：决策历史归 ADR / commit；决策变更时原位改写为新决策，不留旧文、不追加日期流水。
5. **存量不批量清理**：新写 / 触碰到的代码执行本规约，不符者随手修正。
